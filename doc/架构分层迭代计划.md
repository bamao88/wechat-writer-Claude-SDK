# 微信公众号 AI 写作系统 — 架构设计文档 v2

> **核心原则：代码负责框架的稳定性（死逻辑），AI 负责内容的方向性（活决策）。**

---

## 一、系统概览

本系统采用 **"枢纽-分支" (Hub-and-Spoke)** 分层编排架构，基于 Claude Code SDK 实现，将写作流程拆解为：策略规划 → 并行调研 → 素材合成 → 风格写作 → 质量评审 五个阶段，支持动态路由与自动降级输出。

```
选题输入
   │
   ▼
[Planner]  ──→  决定调研路径
   │
   ├── use_private=true  →  [Miner]   (挖掘私域知识库)
   ├── use_web=true      →  [Web]     (全网调研)
   │         ↓ 并行执行，结果汇入 State
   ▼
[Orchestrator]  ──→  逻辑排布，输出写作大纲
   │
   ▼
[Writer]  ──→  风格化写作，输出完整文章
   │
   ▼
[Critic]  ──→  质量评审，打分 + 失败原因
   │
   ├── 达标  →  输出最终文章
   └── 不达标（循环 ≤3 次）→ 将 reason 注入 State，返回 Writer 定向重写
              循环超限  →  DEGRADED_OUTPUT（输出最后一次结果 + 日志标记）
```

---

## 二、Agent 角色与职责边界

| Agent | 层次 | 核心职责 | 边界（不干什么） |
|---|---|---|---|
| **策划代理 Planner** | L1 策略层 | 分析选题，决定调研路径，输出执行计划 JSON | 不接触具体素材，不搜索 |
| **私域挖掘员 Miner** | L3 执行层 | 调用 NotebookLM，提取个人观点、金句与原话片段 | 不负责全网搜索，不构思 |
| **全网调研员 Web** | L3 执行层 | 搜索实时热点、行业数据与外部案例 | 不接触私域库，不写作 |
| **总编辑 Orchestrator** | L3 执行层 | 将 Miner / Web 素材合成，排布写作大纲 | 不直接写长文，只出逻辑骨架 |
| **风格执笔人 Writer** | L3 执行层 | 依据大纲与原话片段风格化写作；重写时接收 Critic 反馈定向修改 | 不核实事实，完全依赖上游 |
| **审计员 Critic** | L3 执行层 | 规则检查 + 评分，输出结构化结果供 Executor 路由 | 不做任何创作，不直接调用其他 Agent |

## 三、Planner 调研路径决策

Planner 输出一个标准化 JSON，驱动 Executor 的调度逻辑。

### 3.1 四种路径

```json
{ "use_private": false, "use_web": false }   // 纯 AI 写作（用户提供了充足上下文）
{ "use_private": true,  "use_web": false }   // 只挖私域
{ "use_private": false, "use_web": true  }   // 只搜全网
{ "use_private": true,  "use_web": true  }   // 全量调研（默认推荐）
```

### 3.2 决策输出格式

```json
{
  "use_private": true,
  "use_web": true,
  "reason": "选题涉及个人经历且需要实时数据佐证，建议全量调研"
}
```

### 3.3 "纯 AI 写作"路径的风险约束

在 Planner 的 system prompt 中明确：

> **只有当用户在输入中已提供充足背景素材（≥300字上下文）时，才允许 `use_private=false, use_web=false`。否则至少启用一个调研路径。**

`reason` 字段会写入日志，供事后审查 Planner 决策是否合理。

## 四、Miner 的双层输出（风格保留方案）

NotebookLM 返回的素材包含大量本人讲话的转录，直接摘要会丢失个人语气。
Miner 采用**分层输出**，将结构化信息与原声片段分开传递：

```json
{
  "structured_points": [
    "观点A：...",
    "观点B：..."
  ],
  "raw_voice_clips": [
    "你知道吗，我当时就在想这件事根本不是技术问题...",
    "很多人都误解了，其实核心在于..."
  ]
}
```

| 字段 | 传递给 | 用途 |
|---|---|---|
| `structured_points` | Orchestrator | 逻辑排布，构建文章骨架 |
| `raw_voice_clips` | Writer | 保留原声语气，化用原话措辞 |

**相关性筛选**：Miner 在返回前只保留与本次选题**强相关**的原话片段，避免将无关转录内容传入下游，控制 Writer 的上下文体积。

Writer 的 prompt 明确要求：

> **请以 `raw_voice_clips` 中的语气和措辞风格来写作，可直接化用这些表达，使文章读起来像作者本人所写。**

## 五、上下文裁剪策略

裁剪在**每个 Worker 输出时**完成，而不是在跳转前统一压缩。

**原则：垃圾在源头处理，不在终点堆积。**

| 位置 | 做法 |
|---|---|
| Miner 输出 | 只返回与选题相关的结构化观点 + 精选原话片段（≤500字） |
| Web 输出 | 只返回核心数据点与案例摘要（≤500字） |
| Orchestrator 输出 | 输出紧凑大纲（≤800字），不含原始素材 |

实现方式：在每个 Worker 的 system prompt 末尾加一条约束即可，无需额外模块。

## 六、Critic 质量评审与回溯机制

### 6.1 现阶段方案：规则检查为主

MVP 阶段不引入 LLM 评审，使用代码规则检查，稳定且成本低：

| 检查项 | 规则 | 不达标行为 |
|---|---|---|
| 字数 | 正文 ≥ 800 字 | 触发重写 |
| 结构完整性 | 包含标题、引言、正文段落、结尾 | 触发重写 |
| 关键字段 | 大纲中的核心论点在正文中均有体现 | 触发重写 |

### 6.2 Critic 评分输出格式

```json
{
  "score": 6,
  "passed": false,
  "reason": "结尾逻辑断层，未呼应开头的核心问题"
}
```

### 6.3 回溯实现：Critic 不调用 Agent，只写 State

Critic 本身不直接调用其他 Agent，**回溯逻辑完全在 Executor 的 `while` 循环里实现**。Critic 只负责输出结构化评分，Executor 负责解读信号并跳转：

```python
# executor.py 核心循环（伪代码）

MAX_ITERATIONS = 3
state.iteration_count = 0
state.next_step = "writer"

while state.next_step != "done":

    if state.next_step == "writer":
        output = writer_worker.run(state)
        state.draft = output
        state.next_step = "critic"

    elif state.next_step == "critic":
        result = critic_worker.run(state)   # 返回 {score, passed, reason}
        tracer.append_critic_result(
            cycle=state.iteration_count,
            score=result["score"],
            passed=result["passed"],
            reason=result["reason"]
        )

        if result["passed"]:
            state.next_step = "done"

        elif state.iteration_count >= MAX_ITERATIONS:
            tracer.save_article(state.draft, degraded=True)
            state.next_step = "done"

        else:
            # 回溯：将 reason 注入 State，Writer 下一轮定向修改
            state.critic_feedback = result["reason"]
            state.iteration_count += 1
            state.next_step = "writer"
```

**关键：`critic_feedback` 必须写入 State**，Writer 的 system prompt 需包含：

```
{% if critic_feedback %}
上一轮审稿意见：{{ critic_feedback }}
请针对以上问题修改，其余部分保持原有风格。
{% endif %}
```

这样每次回溯 Writer 都知道具体哪里没过，而不是盲目重写整篇。

## 七、路由信号约定

Agent 在输出中携带状态标识，Router 用正则提取：

```xml
<status>PASS</status>
<status>NEED_REWRITE</status>
```

Executor 根据信号在 `while` 循环中更新 `next_step`，是唯一的跳转控制点。

## 八、可观测性：OutputTracer

系统基于 Claude Code SDK 的 hook 机制实现 `OutputTracer`（`src/utils/trace.py`），输出至 `output/` 目录。

### 8.1 输出文件

| 文件 | 内容 |
|---|---|
| `thought_trace.md` | 完整执行日志，含执行摘要（mermaid 调用链 + 耗时表格）+ 分步骤折叠记录 |
| `article.md` | 最终文章，降级时文件头部附有警告标记 |
| `agent_inputs.json` | 所有 Agent 调用的结构化输入记录，便于离线分析 prompt 质量 |

### 8.2 针对本架构的三处扩展

**① 降级标记**

`save_article` 支持 `degraded` 参数，触发时在文件头部写入警告：

```python
def save_article(self, content: str, degraded: bool = False) -> Optional[str]:
    prefix = "> ⚠️ DEGRADED_OUTPUT：已达最大重写次数，输出最后一次结果\n\n" if degraded else ""
    # 写入 prefix + content
```

**② Critic 专用记录方法**

新增 `append_critic_result`，将每轮评审结果以结构化表格写入 trace：

```python
def append_critic_result(self, cycle: int, score: int, passed: bool, reason: str) -> None:
    self._seq += 1
    status = "✅ PASS" if passed else "❌ NEED_REWRITE"
    block = TRACE_ENTRY_WITH_AGENT.format(
        seq=self._seq, ts=self._timestamp(), agent="Critic", kind="Quality Check"
    )
    block += f"| 轮次 | 评分 | 状态 | 原因 |\n|---|---|---|---|\n"
    block += f"| Cycle {cycle} | {score} | {status} | {reason} |\n\n"
    self._append_to_trace(block)
```

**③ 摘要补充重写轮次统计**

`_generate_summary` 的 Agent 详情表格新增 `重写轮次` 列，并对 DEGRADED 行标注，一眼识别质量问题文章。

### 8.3 Trace 路径示例

```
Topic → Planner (full_research)
      → Miner + Web (parallel)
      → Orchestrator
      → Writer
      → Critic (Cycle 0 | score=5 | ❌ NEED_REWRITE | 缺乏具体案例)
      → Writer (critic_feedback 注入)
      → Critic (Cycle 1 | score=6 | ❌ NEED_REWRITE | 结尾逻辑断层)
      → Writer (critic_feedback 注入)
      → Critic (Cycle 2 | score=6 | ❌ NEED_REWRITE | 结尾逻辑断层)
      → ⚠️ DEGRADED_OUTPUT
```

通过每轮 Critic 的 `reason` 可快速判断：是 Writer 的 prompt 需要优化，还是 Orchestrator 的大纲结构有问题。

## 九、代码模块结构

```
src/
├── agent/
│   ├── planner.py           # 策略层：分析选题，输出调研路径 JSON
│   ├── executor.py          # 执行引擎：while 循环，唯一路由控制点
│   ├── router.py            # 路由模块：解析 XML 状态标识，决定 next_step
│   ├── state.py             # 状态中心：共享内存，含 critic_feedback 字段
│   └── workers/
│       ├── miner.py         # 私域挖掘员：调用 NotebookLM，双层输出
│       ├── web.py           # 全网调研员：调用搜索工具
│       ├── orchestrator.py  # 总编辑：逻辑排布，输出大纲
│       ├── writer.py        # 风格执笔人：支持接收 critic_feedback 定向修改
│       └── critic.py        # 审计员：规则检查，输出评分 JSON
├── tools/
│   ├── notebooklm.py        # NotebookLM API 封装（响应较慢，建议异步）
│   ├── tavily.py            # Tavily 搜索封装
│   └── serpapi.py           # SerpAPI 搜索封装
└── utils/
    └── trace.py             # OutputTracer：基于 SDK hook，记录完整执行链路
```

## 十、State 核心字段定义

```python
@dataclass
class State:
    # 输入
    topic: str                        # 用户提供的选题
    user_context: str                 # 用户附带的上下文素材

    # Planner 决策
    use_private: bool
    use_web: bool
    planner_reason: str

    # 调研素材（Miner 双层输出）
    structured_points: list[str]      # 结构化观点，给 Orchestrator
    raw_voice_clips: list[str]        # 原话片段，给 Writer

    # Web 调研结果
    web_research: str                 # 摘要，≤500字

    # 写作中间产物
    outline: str                      # Orchestrator 输出的大纲
    draft: str                        # Writer 输出的正文

    # 质量评审与回溯
    critic_score: int
    critic_reason: str
    critic_feedback: str              # 注入 Writer prompt 的定向修改意见
    iteration_count: int              # 当前重写轮次（上限 MAX_ITERATIONS=3）

    # 系统状态
    next_step: str                    # 当前路由目标
    status: str                       # PASS / NEED_REWRITE / DEGRADED_OUTPUT
```
